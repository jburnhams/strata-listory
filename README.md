# Strata Listory

A local-first app to catalogue and process my audiobooks. This is the first step: a catalogue of books (CLI, HTTP API and web UI) on top of a Python + React stack. Processing (scanning a folder of audio files, reading tags, chapters, conversion) comes next.

The stack comes from the `python-app-template`: a FastAPI backend and CLI (`src/app/`), a React 19 + TypeScript + Tailwind CSS v4 frontend (`web/`) that builds into the Python package, hermetic unit and integration test suites (pytest + hypothesis, Vitest + Testing Library + MSW), ratcheting coverage gates, and multi-OS GitHub Actions CI.

## Quick start

```bash
scripts/setup_env.sh                          # macOS / Linux (or scripts\setup_env.ps1 on Windows)
./app doctor                                  # check the environment
./app add "Dune" --author "Frank Herbert" --series Dune --series-position 1
./app list                                    # the catalogue (search with ./app list herbert --status unlistened)
./app backup                                  # back up the database now (also automatic daily)
./app set library_dir ~/audio                 # where the audiobooks live
./app scan                                    # find books (read-only), add them as `new`; --dry-run just counts
./app providers                               # which metadata providers can run
./app match                                   # look new books up with them and record suggestions
./app match-test --limit 60 --stride 25       # compare providers on a sample, records nothing
./app list --review suggested                 # check them; ./app confirm ID applies a suggestion, ./app ignore ID drops one
./app serve                                   # web UI + API on http://127.0.0.1:8360/
```

For hot-reload frontend development, run `./app serve` in one terminal and `cd web && npm run dev` in another (Vite proxies `/api` to `127.0.0.1:8360`).

## Assumptions in this first step

There was no feature list, so these are guesses to be corrected:

- Single user, local-first, no accounts; data lives in `data/catalogue.json` (or the folder set with `./app set data_dir`), a SQLite database (WAL mode). Keep the data folder on a local disk, not an SMB share, because SQLite locking is unreliable over SMB.
- A book has: title (required), author, narrator, series and position, duration, path to the audio, and a listening status (`unlistened`, `listening`, `finished`). Titles are not unique, so an audiobook can be catalogued twice.
- Books can still be entered by hand. Scanning reads folder and file names only (no tags or durations yet) and never writes to, moves or deletes audio files.
- `library_dir` ("audiobook folder") is the folder `scan` walks. Tested against a ~430 GB library of ~28,000 files: about 5,700 candidates, roughly 2,300 books and the rest radio/podcast episodes (kind `radio`, never looked up).
- **Scan heuristics** (`src/app/scan.py`): a single `.m4b`/`.m4a` is a book; a folder of numbered or chapter-named mp3s is one book; folders split as CD1/CD2, "(Disc 3)" or "Title 02-10" are one book; a folder of unrelated tracks gives one candidate per file. Titles, authors, ASINs (`[B004EVP6BY]`), series numbers and "read by" are parsed from names like `Author 2008 Title [ASIN]`, `Author - Title (Unabridged)` and `Title by Author`. Expect some mistakes, which is why everything starts as `new` and goes through review.
- **Matching** (`src/app/matcher.py`, providers in `src/app/providers/`): several metadata providers behind one interface. `./app providers` lists them and whether each can run. Today: **Audnexus** (exact ASIN lookup, open community API in front of Audible), **Audible catalogue** (title and author search; returns ASIN, authors, narrators, series, runtime and cover; public but unofficial), **Hardcover** (GraphQL; title/author search, ASIN lookup, covers, and the community data below; free API token in `~/.config/strata-listory/hardcover.key` or `APP_HARDCOVER_KEY`, about one request a second) and **AudiobookDB** (title search and ASIN lookup, needs a free API key in `~/.config/strata-listory/audiobookdb.key` or `APP_ADB_KEY`, personal use only). Choose and order them with `./app set match_providers audible,audiobookdb` (or `APP_PROVIDERS`); `audible_region` picks the Audible store (default uk).
  - An ASIN in the folder name is asked of each provider in order, and the first hit wins.
  - Otherwise every provider is searched with the title and author, in order, and each candidate is scored on title and author similarity. The same book found by several providers is merged (missing fields filled in from each, small bonus for agreement). A near-certain answer from an earlier provider ends the search early. The best candidate scoring 0.6 or more becomes the *suggestion*, with the providers that found it and up to three alternatives; 0.85 or more is "likely right". A suggestion changes nothing until confirmed (confirming applies title, author, narrators, series, ASIN and, if unknown, the runtime). A provider that is down is skipped; if all are down the run stops and says so.
  - `./app match-test --limit 60 --stride 25` compares the providers alone and combined on a sample of scanned books without recording anything.
  - Add a provider by writing a `Provider` subclass (`providers/base.py`: `search`, `by_asin`, `unavailable`) and listing it in `providers/__init__.py`. Responses are cached 7 days; each provider is rate limited and retried on 429/5xx.
  - AudiobookDB's terms: personal, non-commercial use, attribution shown in the UI.
- **Book page** (`#/book/ID`, `/api/books/ID/details`): all the metadata available for a book: catalogue fields; the Audible `*.metadata.json` file that sits next to purchased books (narrators, series, publisher, release date, runtime, rating, categories, summary, chapters; about 118 of the library's books have one); the audio files with sizes; embedded tags, codec, bitrate and exact duration from `ffprobe` (cached until the files change; needs ffmpeg installed); and the AudiobookDB suggestion. Opening the page fills in `duration_seconds` when it was empty.
- **Covers** (`/api/books/ID/cover`, thumbnails in the library): taken in this order, and saved once in the book's mirror folder (below): a picture in the book's folder (cover/folder/front, else any picture; for a loose file only one with the same name), art embedded in the audio, the cover URL in the book's own Audible metadata file, then the providers' covers for its match (confirmed, or 85%+): the suggestion's own, then each provider by ASIN (Audnexus, Audible, AudiobookDB) and AudiobookDB by id. The source is recorded in `metadata.json` (`cover_source`). AudiobookDB's terms do not license its images (§5.1: users must obtain those rights themselves); using them is a deliberate choice for this private catalogue.
- **Data mirror** (`src/app/mirror.py`): the audio share is read-only, so each book's data lives in a tree under `<data_dir>/library/` that mirrors the audio library: `<path relative to library_dir>/metadata.json` (final catalogue record, the match that produced it, the Audible metadata summary, cover source) and `cover.jpg|png`. A single-file book gets a folder named after the file; books outside the library go under `_external/`, hand-entered ones under `_manual/ID-title/`. It is written whenever a confirmed book is added or changed and when a cover is saved; `./app mirror [--all]` rewrites it from the database (which stays the source of truth). It is plain files, so it is covered by the nightly restic backup of the data folder.
- **Ratings and reviews** (`src/app/enrich.py`): for confirmed books, `./app enrich [ID]` (or the book page's *Fetch from Hardcover* button, `POST /api/books/ID/enrich`) stores Hardcover's community data: rating, rating/review/reader counts, genres, moods, content warnings, tags, description, series, audiobook editions and the five most-liked public reviews (spoiler reviews are collapsed). Which Hardcover book is ours is decided from the suggestion, then ASIN, then a title/author search that must score as a likely match; a book that cannot be placed is remembered as not found. Data is refreshed after 30 days, shown on the book page with a link to hardcover.app, and written to the book's mirror `metadata.json`. Reviews are the readers' own words, kept in this private catalogue with the reviewer's name.
- **Approval queue (manual, for now):** nothing is processed automatically. `./app process-propose` (or *Find candidates* on the **Processing** page) plans eligible books (confirmed by you, with a title and author, not radio) and puts the plans in a queue; each shows hours, chapters and where they came from, the quality tiers, the estimated size before and after, the loudness change and any warnings, with the chapter list on demand. You approve or reject (a rejected book is not proposed again; *Plan again* throws a plan away, for example after fixing metadata). Only *Process approved* (or `./app process-run`) runs the approved plans, one background worker in the app at a time, with progress on the page; a plan whose files have changed since it was proposed refuses to run and asks to be planned again. The queue states are `proposed -> approved -> running -> done | failed` (or `rejected`). CLI: `process-propose`, `process-queue [--state S]`, `process-approve IDS`, `process-reject IDS`, `process-run`. Making this automatic later is a matter of approving by rule (for example high-confidence matches); the plan, checks and recording stay the same.
- **Processing into the final library** (`./app process`, `src/app/process/`): turns books into mono mp3 chapter files in `final_dir` (default `~/audiobooks/<Author>/[<Series>/]<Title>/NN - Chapter.mp3`, plus `cover.*`, `playlist.m3u8` and `metadata.json`). It only reads the inbox. `./app process --plan [IDS]` measures and prints what would be done (chapters, tiers, loudness, estimated size) without changing anything; `./app process IDS [--jobs N] [--force]` processes the named books directly (an explicit choice that skips the queue; with no ids it explains the queue); `./app process-status` summarises. Only books you have confirmed are picked up automatically, so only matches and metadata you trust are processed. Decisions, all recorded in each book's `metadata.json` and shown on its book page:
  - **Chapters**, first source that exists: chapters embedded in a single file (`.m4b`); the Audible metadata file's chapter list (if it matches the audio length); the files themselves (tiny ones such as credits are merged into the chapter next to them, which is named after the longer part); pauses of 1.5 s or more in a single long file. Chapters over 75 minutes are split again at pauses (12 to 40 minutes on).
  - **Copy, don't re-encode:** a mono mp3 at or below 96 kbps is cut on frame boundaries (stream copy) and gained losslessly with `mp3gain` in 1.5 dB steps, never past the true-peak limit. Everything else is decoded, downmixed to mono (a stereo book whose channels cancel in a mono mix uses the left channel and says so), gained, limited and encoded with LAME VBR.
  - **Quality per chapter:** speech (silent at least 2% of the time) gets V5 at 24 kHz (about 49 kbps); music-like chapters (almost no pauses) keep more of the top end: V4 at 32 kHz, or V3 at 44.1 kHz when they have a lot of energy above 10 kHz. Thresholds were calibrated on real excerpts (see `plan.py`); the energy-above-10 kHz measure alone does not separate speech from music, pauses do.
  - **Loudness:** the target is -18 LUFS (measured with ffmpeg `ebur128`), with one gain per book so chapters keep their level relative to each other, and a tolerance band: a book at most 3 dB quieter or 2 dB louder than the target is left exactly as it is. Louder than the band: attenuated (lossless for copied files). Quieter than the band: lifted, but copied files only within the true-peak headroom (lossless 1.5 dB steps); if that still leaves the book more than 3 dB short, the whole book is re-encoded despite the bitrate rule so a limiter can lift it. How far is measured from the book's own peaks: the lift is allowed until the 99th-percentile peak would be reduced by more than 2 dB (or the loudest peak by more than 7 dB), so the limiter only shaves isolated peaks (`SQUASH_DB`, `MAX_REDUCTION` in `plan.py`; raise `SQUASH_DB` to reach the target more often at the price of more limiting). Measured on a real book: -23.2 to -18.1 LUFS, loudness range 6.6 to 6.1 LU, true peak -1.2 dBTP. If peaks still stop it reaching the target it simply stays a little quiet: no compensation tags, and the plan says so. Quieter is preferred to clipping.
  - **No clipping:** a hard rule. Copied chapters are only ever gained within the true-peak headroom (and `mp3gain -k` refuses anything that would clip); encoded chapters pass a look-ahead limiter set 0.8 dB under the -1.5 dBTP limit to allow for the encoder's overshoot. Then the finished book is measured again, and if its true peak is above -1.0 dBTP it is rebuilt with less gain (up to twice; noted in the result); if it still cannot be made safe it is not written at all. Loud sources that need to come down are simply attenuated. A source that already reaches full scale is flagged in the plan (it is probably clipped; that cannot be repaired).
  - **Checks:** every output must be readable, mono and add up to the input length (within a second and a bit); the book is written into a `.partial` folder and moved into place only when complete; a failure leaves nothing behind. Measured on two real books: 8.0 h Audible title 435 MB to 204 MB at -18.0 LUFS in 2 minutes; an 11 h book of 64 kbps mp3 copied unchanged (319 MB to 318 MB) with a lossless +1.5 dB.
- **Local copy of the audio share:** the app works from `~/audio-local`, a one-way mirror of the read-only share made by the `audio-sync` job on beelink (`~/.local/bin/audio-sync`, nightly timer at about 03:30, tracked in dotfiles; `audio-sync status` shows the last run). It is `rsync` from the share to local disk only: never written back, deletions are applied only after the transfer and capped per run (`--max-delete`), and it refuses to run when the share looks unmounted or much emptier than last time, so a dead server can never empty the copy. `./app use-library ~/audio-local` switches the app over once the copy is complete: it checks that the books' files exist in the new folder, backs up the database, moves every book path and sets `library_dir`. The mirror folders under `data/library/` are named by path relative to the library, so they are unchanged by the move. With the local copy the file-reading features (scan, tags, embedded covers, book page) no longer depend on the server being up; only the nightly sync does.
- **When a network share is down** (`src/app/fs.py`): every access to files on a network mount first asks `fs.reachable`, which probes the mount from a helper thread with a 4 s timeout, remembers the answer for a few seconds (down: 15 s, up: 10 s) and never piles up probes on a hung mount. A down share means: the book page says so and still shows everything else; covers already in the mirror keep working, and missing ones are simply tried again later (no "no cover" is remembered); `scan` stops with a clear message and changes nothing (a scan interrupted midway is discarded rather than stored half-done); the mirror keeps the Audible summary it already had; backups go to the local folder. Matching, enrichment, the catalogue and the mirror need no share at all. The database, covers and mirror live on the local disk under the data folder.
- **Provider limits:** each provider declares its own request interval and cache lifetime (Audnexus and Audible: 1 request per 0.3 s, cached 14 days; Hardcover: 1 per 1.1 s, cached 14 days; AudiobookDB: 1 per 0.15 s, cached 7 days as its terms ask) and the HTTP client throttles, retries 429/5xx and caches accordingly; `./app providers` shows them.
- **Review states:** `new` (scanned), `suggested` (a match awaits review), `confirmed` (accepted, or entered by hand), `ignored`.
- **Backups:** (if the configured backup folder is unreachable, for example a share that is down, the backup goes to `<data_dir>/backups` instead and the app still starts) the database is checked for corruption when a process first opens it (a corrupt one is refused with advice to restore), and a verified copy is taken automatically at most once a day, before a schema migration and before a restore, into `<backup_dir>` (default `<data_dir>/backups/`; `./app set backup_dir /path` moves it, e.g. to a network share: backups are built and checked on the local disk, then copied there). Kept: the newest of each of the last 7 days and 4 weeks, plus manual and safety copies for 30 days. `./app backup` backs up now, `./app backups` lists them, `./app restore [file]` restores (default newest; the current database is kept as a `pre-restore` copy). On the default they share the database's disk, so they protect against corruption and mistakes, not disk loss; point `backup_dir` at another disk or share for that.

```bash
pip install -r requirements-test.txt
pytest tests/unit --cov                 # unit tests + coverage (CI gates on fail_under in pyproject.toml)
pytest tests/integration -n auto        # CLI and HTTP API end-to-end
ruff check src tests
cd web && npm run test:coverage:gate    # web unit + jsdom integration tests against coverage-floor.json
```
